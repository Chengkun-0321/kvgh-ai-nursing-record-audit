# ADR 0009：領域運算與驗證一律在後端，前端只負責渲染

- 狀態：提議
- 日期：2026-11-10

## 背景

使用者要求「後端處理資料，前端只渲染網頁」。2026-11-10 檢查時，前端有三類不屬於渲染的工作：

**1. 領域運算放在前端**
- `lib/verdict.ts` 算出以下結果：
  - 每床的最嚴重判定
  - 各狀態的床數
  - 待處理床數
  - 摘要文字，例如「缺漏 1 項・需確認 2 項」
- `lib/patient.ts` 算出住院天數與年齡層。

**2. 同一套規則前後端各寫一份**
- 涵蓋的規則：
  - LLM 設定表單的驗證，例如網址格式、逾時 5–600 秒、各服務類型的必填欄位
  - 各服務類型的顯示名稱
  - 對話與 system prompt 的字數上限
- 副本分散在 `llmConfigForm.ts`、`llmConfigWizard.ts`、`llmProviders.ts`、`availableModels.ts`、`constants.ts`。
- 兩邊靠註解「與後端一致」提醒同步。一旦漏改，前端判定可以送出的資料，後端仍會拒絕，或反過來。

**3. 病床資料是前端寫死的 W51 假資料**
- 假資料放在 `mockWardData.ts`，後端沒有病房 API。

## 決策

1. **領域運算只在後端**：
   - 病床總覽 `GET /api/v1/wards/{ward_code}/bed-board` 回傳算好的以下內容：
     - 病床狀態、各狀態床數、待處理床數
     - 摘要文字、住院天數
     - 稽核結果清單為空時的提示文字
   - 原始資料頁的以下內容由後端整理（見 ADR 0010）：
     - 跨日合併與去重
     - 排序與篩選
     - 依日分組
     - 檢驗矩陣
     - 異常標記（↑↓）的解析
2. **驗證規則只有後端一份**：
   - `GET /api/v1/llm-providers` 提供以下內容，前端不再存副本：
     - 服務類型目錄：顯示名稱、欄位是否需要、預設位址、範例
     - 精靈步驟
     - 各項長度上限與提示文字
   - `POST /api/v1/llm-configs/draft-checks` 檢查精靈表單（只檢查、不儲存），回傳以下內容：
     - 逐欄錯誤（依畫面順序）
     - 已儲存金鑰的遮罩值，以及是否沿用
     - 建議名稱
     - 模型清單的查詢方式
     - 確認摘要
   - 規則沿用 `providers.py`（必填欄位）、`schemas/llm_config.py`（位址格式）、`core/constants.py`（長度與逾時上限），與儲存時是同一組常數。
   - `tests/api/v1/test_llm_draft_checks_api.py` 驗證「檢查通過的表單，儲存時不會因長度或格式被拒」，例如 `test_lengths_match_save_limits`。
   - 已儲存設定的摘要與服務名稱，隨 `LlmConfigRead` 一起回傳（`provider_label`、`summary_rows`）。
3. **前端可以做的事**（判定標準：不需要領域知識、換一個病房或換一套規則也不用改）：
   - 排版與顯示對照：例如狀態對應的顏色與圖示、↑↓ 對應的顏色、日期格式化。
   - 畫面狀態：例如篩選造成的淡化、選取的床位、表單草稿、切換服務類型時清空欄位。
   - 頁面路由：網址中的檢視名稱無效時回到時間軸。日期與類別則照原樣交給後端；格式錯誤由後端回報，前端不會默默改成「不篩選」。
   - 組裝請求：把表單欄位放進 API 需要的格式。
   - 3D 場景的版面與相機計算（`wardLayout.ts`、`wardProjection.ts`）。這屬於畫面呈現，不是領域運算，維持在前端。
4. **錯誤在按「下一步」時顯示**：
   - 前端在使用者停止輸入 500 ms 後請後端檢查整份表單，結果只用來顯示摘要、決定是否查詢模型清單，不顯示錯誤。新結果回來前沿用上一次結果，畫面不會閃回「載入中」。
   - 按「下一步」時，前端以該步驟送出檢查，再顯示錯誤並把焦點移到第一個錯誤欄位。
   - 檢查 API 失敗（例如後端未啟動）時，按「下一步」會顯示錯誤訊息並停在原步驟，不會略過檢查直接前進；停止輸入後的檢查失敗則沿用上一次結果。

**考慮過的替代方案**

| 方案 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 保留前端即時驗證，後端為最終判定 | 錯誤即時出現，不需往返 | 規則仍是兩份，需靠人工同步 | 不採用，使用者選擇「全部交給後端」 |
| B. 規則寫成共用的 JSON Schema，前後端各自執行 | 規則只有一份定義 | 「欄位是否需要依服務類型而定」「沿用已儲存金鑰」等規則難以用 schema 表達，且仍有兩個執行器 | 不採用 |
| C. 後端檢查 API（本決策） | 單一來源、單一執行器 | 每次檢查多一次往返 | 採用 |

## 影響

- **好處**：
  - 規則只有一個來源與一個執行器。
  - 原本前端的驗證測試案例（`llmConfigForm.test.ts`、`availableModels.test.ts` 與 `llmConfigWizard.test.ts` 的驗證部分）已改寫為後端 API 測試。前端只保留「切換服務類型」的表單狀態測試。
- **代價**：
  - 錯誤要等後端回應才顯示。2026-11-10 在開發機上以 curl 量測 `draft-checks` 5 次，中位數 1.1 ms（不含瀏覽器與網路），實際感受取決於部署環境。
  - 精靈在輸入停頓後會呼叫檢查 API。表單含 API 金鑰，所以檢查 API 用 POST，金鑰不會出現在網址。
  - 後端無法連線時，設定精靈無法前進。頂部導覽的待處理床數改為隱藏，不影響其他頁面。
- **後續**：
  - 稽核規則實作後，`bed-board` 的 `status`、`pending_findings` 改由 `audit_findings` 產生；回應格式不變。
  - 新增需要判斷的畫面時，先在後端 API 加欄位。
