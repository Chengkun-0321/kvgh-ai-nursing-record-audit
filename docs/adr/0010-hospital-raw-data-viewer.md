# ADR 0010：院方原始資料檢視（直接讀檔、不入庫）與欄位對應

- 狀態：提議
- 日期：2026-11-10

## 背景

- 院方提供 W63 病房 2026-11-04、11-05 兩天的資料。使用者確認院方已移除個人資料。
- 資料的存放結構：
  - 路徑為 `data/<YYYYMMDD>/<病房>/`。
  - 每天有一個 `patientlist.json`（病人清單），另有每位病人一個 `<HCASENO>_<HHISNUM>.json`。
- 識別欄位：
  - HCASENO、HHISNUM 是院方 patientlist 的兩個識別欄位。
  - 院方尚未提供欄位定義。依命名推測，HCASENO 是住院序號，HHISNUM 是病歷號，**待院方確認**。
- JSON 不好人工閱讀。使用者需要一個「原始資料」分頁，看這個病房所有日期的資料。
- 格式特性：用程式統計欄位結構、型別與筆數，沒有閱讀病人內容。

| 特性 | 驗證方式與結果 |
|---|---|
| 每天的檔案只含當天紀錄，「檢查」除外 | 取兩天都在的 40 位病人的 11/05 檔，統計各區塊的日期範圍：護理記錄、生命徵象、檢驗報告、每日身評、用藥都只有 2026-11-05；檢查為 2026-10-10 至 11-05。因此「歷史資料」必須跨日期合併並去重 |
| 床號寫法不同 | patientlist 只寫床位（`001`，41/41 筆），病人檔寫 `W63-001` |
| 沒有姓名、性別、年齡、診斷、病房名稱的欄位 | 82 份病人檔的「病人基本資料」都只有入院時間、床號兩個欄位；其他區塊的文字內容是否含這些資訊未檢查 |
| 「護理記錄」可能是字串 | 75 份為陣列，7 份為字串（「無記錄」） |
| 檢驗報告的鍵不固定 | 共 1,233 筆：640 筆為「日期＋一個項目（動態鍵）＋範圍＋異常值」，593 筆只有「日期＋項目」；異常值為 `No`／`Yes (↑)`／`Yes (↓)`；17 筆項目名為空字串 |

## 決策

1. **直接讀檔、不建資料表**：
   - 這頁的目的是忠實呈現院方原檔。
   - 匯入 DB 的資料表要等匯入流程與稽核需求確定後再設計，見 data-ingestion.md 的規定，以及 `feat/spec-driven-flow` 分支的草稿。
2. **讀檔集中在 `services/hospital_data/source.py`**：
   - 只讀不寫。
   - 日期、病房、檔名都先比對格式。patientlist 與病人檔解析後的實際路徑，都要確認仍在資料目錄內，防止路徑穿越與指向外部的符號連結。
   - 八位數但不是合法日期的資料夾直接略過。
   - 依「路徑＋修改時間」快取解析結果。
   - 同步檔案 I/O 一律放到 thread 執行。
   - 資料目錄由 `HOSPITAL_DATA_DIR` 設定，預設為 `<專案>/data`。
3. **病人識別**：
   - `patient_key` 使用 HCASENO，會出現在網址。
   - HHISNUM 欄位不讀入。但病人檔的檔名含有 HHISNUM，檔名只在後端內部用來開檔：不放進 API 回應、網址或 log。讀檔失敗時轉成不含路徑的錯誤訊息。
4. **欄位對應**（院方 → glossary）：

   | 院方區塊 | 類別（`RawRecordCategory`） | 時間欄 | 標籤 | 標題 | 內文 |
   |---|---|---|---|---|---|
   | 護理記錄 | `nursing_progress_note` | 日期（只有日期） | 類別 | — | 內容 |
   | 生命徵象 | `vital_sign` | 日期 | — | — | — |
   | 每日身評 | `daily_physical_assessment` | 身評時間 | — | — | — |
   | 入院身體評估 | `admission_assessment` | 評估日期時間 | — | — | — |
   | 入院經過 | `admission_course` | 掛在入院時間 | — | — | 各段合併 |
   | 檢驗報告 | `lab_result` | 日期（視為採檢時間，待確認） | — | 「n 項」 | — |
   | GCS | `gcs` | 測量時間 | — | — | — |
   | 用藥 | `medication_order` | 日期 | — | 藥名 | — |
   | 檢查 | `examination` | 日期 | 狀態 | 項目 | 內容 |
   | 會診 | `consultation` | 日期 | 科別 | — | — |
   | 轉床資料 | `bed_transfer` | 操作日期 | — | — | — |

   - 上表區塊中，表格以外的欄位依院方原本的順序成為「項目：結果」，所以這些區塊新增欄位時會自動顯示。
   - 院方若新增**整個區塊**，時間軸不會顯示，要在 `SECTION_SPECS` 補對應；在補上之前，可從「院方原文」看到。
   - 時間一律視為台北時間；無法解析的時間照抄原文。
   - 工作清單取自最新一天的檔案。值只有「有填寫」或「沒有填寫」。

   **轉換範例**（虛構資料）：

   ```
   輸入：11/04 檔與 11/05 檔都有一筆
     檢查 {"日期": "2026-01-01", "狀態": "正式報告", "項目": "胸部X光", "內容": "…"}
   步驟：轉成時間軸紀錄 → 以內容（不含資料日期）算出 event_id → 兩筆 ID 相同，只留一筆，資料日期取 11/04
   輸出：時間軸 2026/01/01 下一張卡片，類別「檢查」、標籤「正式報告」、標題「胸部X光」
   ```

5. **合併與去重**：

   ```
   各日期資料夾 ──讀檔──▶ 各區塊轉成時間軸紀錄 ──以內容去重──▶ 依日分組（新→舊）
                    └─▶ 檢驗結果 ──以「時間＋項目＋結果＋範圍＋異常標記」去重──▶ 依採檢時間分組／檢驗矩陣
   ```

   - 一般紀錄：內容完全相同即視為同一筆，保留最早出現的資料日期。
   - 檢驗結果：上述五項都相同才合併；異常標記不同就不合併。
   - 檢驗矩陣：
     - 同一採檢時間、同一項目有多個不同結果時，同一格全部列出，不互相覆蓋。2026-11-10 的資料中有 18 格是這種情況。
     - 同一項目出現過不同的參考範圍時，全部列出。目前有 3 個項目是這種情況。
6. **API**（皆為 GET）：
   - `/api/v1/wards`
   - `/api/v1/wards/{ward_code}/raw-patients`
   - `/api/v1/raw-patients/{patient_key}`：摘要
   - `/api/v1/raw-patients/{patient_key}/timeline`：可帶起訖日與類別
   - `/api/v1/raw-patients/{patient_key}/lab-matrix`
   - `/api/v1/raw-patients/{patient_key}/source`：原文
7. **首頁改為 W63**：
   - 床位清單來自該病房最新一天的 patientlist，由後端 `DEFAULT_WARD_CODE` 決定。
   - 稽核規則尚未實作，每床狀態為「尚未稽核」（`BedBoardStatus.NOT_AUDITED`）。這不是新的判定等級，Verdict 分級仍是待決事項。

## 影響

- **好處**：
  - 不需要 migration。
  - 院方資料更新後重新整理頁面即可看到。
  - 原文可直接對照時間軸，確認轉換沒有失真。
- **代價**：
  - 每次查詢病人都要掃描各日期的 patientlist，以快取緩解。
    - 2026-11-10 在開發機以 curl 各量 5 次（2 天、41 床、已快取），中位數為：`bed-board` 4.9 ms、`raw-patients` 4.8 ms、`timeline` 3.9 ms、`lab-matrix` 2.7 ms。
    - **切換條件**：任一 API 的中位數超過 500 ms，或資料日期超過 90 天時，改為匯入 DB 後再查詢。
  - 時間、內容完全相同的兩筆一般紀錄會合併成一筆。院方若真有這種重複，時間軸只會顯示一筆；原文仍保留。
  - 病人轉到其他病房時，目前只會找到第一個病房的歷史紀錄。目前只有 W63 的資料，所以還不會發生。
- **待確認**：
  - HCASENO、HHISNUM 的定義，以及 HCASENO 是否適合作為會出現在網址的 `patient_key`。
  - 檢驗報告的「日期」是否為採檢時間。
  - 檢驗報告中名為 `TIME` 的項目（值為 12 位數字），推測是血糖的測量時間，目前照原樣列出。
  - 項目名為空字串的檢驗（17 筆），目前顯示為「（院方未提供項目名）」。
  - 根目錄 `data/` 已進版控。使用者 2026-11-10 確認為去識別化的院方資料，與 security-privacy.md 原本「根目錄 data/ 只放虛構資料」的規定不同，已同步更新該文件。
